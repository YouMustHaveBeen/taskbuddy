# AGENTS.md

Проект: TaskBuddy — единая система дел (GTD) с FlyLady-зонами, рутинами и практиками.
Интерфейсы: Telegram-бот, веб-страница и Claude через MCP-сервер. База одна на всех.
Стек: TypeScript, один Cloudflare Worker (Hono, grammY), D1 + Drizzle ORM, страница на React + Vite.
Вся логика — в `src/core`; SQL — только в `src/db`; Telegram — в `src/telegram`; API страницы — в `src/api`;
MCP — в `src/mcp`; расписание — в `src/jobs`; страница — в `web/`; тексты — в `i18n/`.

Спецификация — два документа Claude Docs:
«Требования к TaskBuddy» (что делает система): https://claude.ai/artifact/3Uyg4TnUxSr6ki5Rj1VUtR
и «Архитектура TaskBuddy» (как строим): https://claude.ai/artifact/GtTi3bqcUP3WrLUzWiJyuy.
Это документы, а не веб-страницы: читать их инструментами Claude Docs. Копии в репозитории (markdown):
`docs/requirements.md` и `docs/architecture.md`, чтобы их видели все агенты и ревьюеры. Источник правды —
Claude Docs; при расхождении действует Claude Docs. Если спецификация изменилась, копии в `docs/`
обновляются в том же PR, к которому относится изменение.
Этот файл спецификацию не заменяет и не дублирует, а добавляет проверяемые правила для работы с кодом и с владелицей.
Отложенные задачи — в `docs/pending.md`. Почему код устроен именно так — в `docs/decisions.md`.

Локальная папка проекта на машине владелицы: `~/YouMustHaveBeen/taskbuddy`. Терминальные команды для нее —
с `cd ~/YouMustHaveBeen/taskbuddy`, не с путем агентского контейнера (`/home/user/taskbuddy` и т.п. —
это не машина владелицы).

## Как работать с владелицей

1. Общаться по-русски, на «ты», коротко.
2. Выполнять инструкции точно. Если есть сомнения — спросить до действия, а не после.
3. Не спорить о принятых решениях. Если владелица говорит, что решение было принято или отменено, — принять
   и применить.
4. Не создавать файлы, документы и артефакты без разрешения владелицы: существующие править можно, новое — только
   после «да». Это касается и агентов-исполнителей: в инструкциях к ним так и писать.
5. Не оставлять заглушек для заполнения («вставь сюда…», `TODO: текст`): давать готовый текст.
6. Нумерация: каждый вопрос и каждое утверждение, требующее реакции, — свой номер. Одна сквозная
   последовательность на весь разговор, только число, без подпунктов и букв; номера не переиспользуются.
   Вопросы — обычным нумерованным текстом в чате, не виджетами.
7. Владелица не программист. Команды давать готовыми, с указанием, где их выполнить. Терминальные команды
   начинаются с `cd` в нужную папку; все команды одной задачи — одним блоком, строка за строкой, без `&&`;
   команда с интерактивным вопросом y/n — отдельным блоком.
8. Не запускать субагентов и большие незаказанные проверки без явного «да» владелицы.
9. Называть, какую модель использовать для задачи и почему. Этап 0, схема, core (выбор дня, права) и OAuth —
   Opus: ошибки там дорогие. Страницы, тексты, рутинные обработчики — можно Sonnet.
10. Если нет доступа к чему-то — самому искать другой способ (другой инструмент, встроенный браузер),
   а не ждать подсказки.
11. Агент не может удалять git-ветки; не предлагать удаление веток.

## Главное правило

12. Не оптимизируй и не рефактори код сверх поставленной задачи.
   Ничего не добавляй от себя: каждая функция, кнопка, проверка и запрос должны соответствовать
   подтвержденному решению и спецификации. Если для задачи нужно что-то, чего в спецификации нет
   или что ей противоречит, — сначала покажи, где именно противоречие, и дождись подтверждения.
   Замечание автоматического ревьюера не является подтверждением: любое изменение поведения сверх узкого
   багфикса называется отдельно и подтверждается отдельно, а не входит в общий пакет под одно «пиши».

13. Перед записью или изменением любого кода/файла задается вопрос «можно писать код?» отдельным сообщением,
   ответ ждется. Ответ на вопрос по содержанию — не разрешение. Вопрос не задается, пока в обсуждении есть
   открытые вопросы, требующие ответа владелицы, — только когда на все получен ответ.

14. Если фикс требует нового или измененного пользовательского текста (кнопки, сообщения бота, надписи страницы),
   текст пишет агент на обоих языках: показать владелице текущий текст, в чем проблема, и предложить новый текст
   на утверждение. В `i18n/` текст попадает только после утверждения владелицей.

15. Буква «ё» не используется нигде: ни в коде, ни в комментариях, ни в `i18n/ru.json` и текстах интерфейса,
   ни в документации — только «е» (например, «Легкая»).

## Этапы

16. Работа идет строго по этапам из «Архитектуры» (раздел «Этапы»); следующий этап начинается только после
   «да» владелицы.

17. Этап 0. Каркас: Worker, D1, миграции, скелет i18n, вход через Telegram для одного пользователя, gitleaks,
   GitHub Actions, этот файл.
18. Этап 1. Инбокс: запись текстом из бота (ответ галочкой), вкладка «Инбокс», карточка с мгновенным сохранением, «+».
19. Этап 2а. Сегодня: пять кнопок «Выдай мне дело», «Выбрать», вечерний опрос, утро, напоминания, вкладки
   «Сейчас», «Сегодня», «Задачи», «Инсайты». Это первая рабочая версия; после нее владелица живет в системе
   неделю, прежде чем добавлять новое.
20. Этап 2б. Таймер, награды, первый шаг, «Парковка».
21. Этап 3. Рутины и зоны FlyLady.
22. Этап 4. GTD целиком: проекты, шаги, «Разбить», «Жду», очередь, категории, автолягушки, обзор.
23. Этап 5. Практики.
24. Этап 6. Claude через MCP: OAuth, команды «Разгрузи голову» и «Разбери инбокс», запуски по расписанию,
   режим обучения.
25. Этап 7. Семья: приглашения, поручения, «Я поручила».
26. Этап 8. Публикация.

27. Не реализовывать раньше времени то, что относится к следующим этапам, разделу «Не реализуем сейчас»
   или «На будущее». Но то, что дешево сейчас и дорого потом, закладывается с этапа 0: `owner_id` и `creator_id`
   у каждой записи, `household_id`, тексты в `i18n/`, числа в настройках, время в UTC.

## Ветки, PR, merge

28. Работа всегда идет через ветку, прямых коммитов в `main` нет. Исключения: правка документации в `docs/`,
   правка дизайна веб-страниц и сообщений бота, прямое указание владелицы.
29. Запрос ревью на уже открытом PR отдельного «да» не требует, но ревью у Copilot не запрашивать никогда.
30. Merge в `main` — только после отдельного явного «да» на каждое слияние.
31. Перед любым PR сверить изменение со ВСЕЙ спецификацией (оба документа), а не только с относящимся разделом.
32. `docs/decisions.md`, `docs/pending.md` и копии спецификации (`docs/requirements.md`, `docs/architecture.md`)
   обновлять в том же PR, а не после слияния.
33. Личные данные: настоящие имя и email владелицы не должны встречаться нигде — ни в коммитах, ни в логах,
   ни в коде, ни в комментариях (код будет опубликован).
34. Коммиты и push делает агент сам, а не владелица. Если доступа к репозиторию с правом push нет, сразу подключить
   его (`add_repo` с `access: push`); не отправлять
   владелицу в терминал за `git push`.

## Данные пользователей и права

35. Каждая запись имеет `owner_id` (чья, кто выполняет) и `creator_id` (кто создал или поручил) с самого начала.
   Видишь запись, если ты ее владелица или автор; больше никто, даже в той же семье.
36. SQL есть только в слое доступа `src/db`. Каждый запрос в нем уже содержит условие «я владелица или автор»;
   запросов в обход слоя нет. На права — отдельный набор тестов, они обязаны проходить.
37. Пользователь всегда берется из проверенного входа (сессия, токен OAuth), а не из того,
   что прислали в теле запроса или в аргументах MCP-вызова.
38. В логи не писать тексты записей, ответы «Что мешает?», первые шаги, `file_id` голосовых, Telegram ID,
   токены и ссылки для входа.
39. Сроки хранения — ровно по «Архитектуре»: архив и отметки рутин старше года удаляются, `daily_stats`
   не удаляется; записи «удалить как неактуальное» не учитываются в статистике и прогрессе. Не добавлять
   поля и таблицы с личными данными, которых нет в схеме.

## Модуль core, бот, страница, MCP

40. `src/core` ничего не знает о Telegram, HTTP и MCP: никаких импортов из `src/telegram`, `src/api`,
   `src/mcp`, никаких их типов и терминов. Все правила (выбор дня, лягушки, переносы, приоритет, зоны, права)
   только в core. Бот, страница и MCP лишь вызывают его.
41. Все вызовы Telegram — только через `src/telegram` (grammY). Прямой `fetch` к `api.telegram.org` вне этого
   модуля запрещен.
42. Вебхук проверяет секретный токен, сразу отвечает Telegram, а долгую работу выполняет в фоне через `waitUntil`.
   Повторные обновления отсекаются по `update_id`.
43. Ответ на нажатие кнопки (снятие «часиков») отправляется как можно раньше, а не после всех чтений из D1,
   если это не меняет бизнес-логику.
44. Новые пользователи — только по коду приглашения; эта проверка одна общая на входе, не дублируется.
45. Страница одна — веб в браузере, мини-приложения Telegram нет. Вход — только по одноразовой ссылке из бота
   (/web или кнопка «Выбрать»), затем выдается токен сессии.
46. MCP: OAuth 2.1, шаблон Cloudflare (Agents SDK, `McpAgent`, `workers-oauth-provider`). При запусках
   по расписанию Claude только читает и сохраняет предложения (`inbox_suggest`): статусы не меняет и ничего
   не удаляет. Помощь Claude получает только владелица подписки, члены семьи доступа к Claude не получают.
47. Бот сам Claude не вызывает: платных вызовов API нет.

## Настройки, время, расписание

48. Все числа и времена правил — не в коде, а настройки: время опроса (21:00), день обзора, горизонт дедлайнов,
   порог лягушки, число замен, веса и уровни приоритета, длины таймеров, размер блока FlyLady, срок архива,
   время запусков Claude, порог обучения, лимит проектов в фокусе и т.д. Значения по умолчанию — в одном файле
   настроек, свои значения пользователя — в таблице `settings`. Новое число в правиле = новая настройка.
49. Все время в базе — в UTC; у пользователя IANA-зона (по умолчанию `Europe/Dublin`); расчеты через `date-fns-tz`.
   Для логики дней и зон — тесты на дни перехода на летнее и зимнее время.
50. Расписание — cron раз в 5 минут. Событие дня берет ровно один запуск: отметка даты в `users` ставится одним
   `UPDATE ... WHERE отметка < сегодня RETURNING`; напоминание снимается `UPDATE tasks SET remind_at = NULL ... RETURNING`.
   Таблицы `jobs` нет.
51. Окончание таймера — точный будильник (alarm в Durable Object), а не проверка cron.

## Языки

52. Все надписи — только в `i18n/ru.json` и `i18n/en.json`. Ни одной пользовательской строки в коде.
53. Склонения — через `Intl.PluralRules`. Тест на совпадение ключей в обоих файлах обязателен.
54. Названия, которые пишет сам пользователь (задачи, рутины, практики), не переводятся.

## Cloudflare и внешние сервисы

55. TaskBuddy — отдельный Worker и отдельная база D1 `taskbuddy`. На том же аккаунте живут другие проекты
   (streetbuddy, gigbuddy, 4602): их Worker, базы, KV, R2, очереди и cron не трогать.
56. Общие квоты аккаунта: 5 ГБ хранилища D1. Не хранить в D1 то, что растет без правила очистки.
57. R2 — только для еженедельной резервной копии. Queues не используются.
58. Голос: Whisper и другие сервисы распознавания не используются нигде. Первый шаг в боте хранится
   голосовым (`file_id` Telegram) без расшифровки. Расшифровка Telegram Premium боту недоступна.
59. Секреты — только через `wrangler secret`, никогда в файлах репозитория. gitleaks проверяет каждый push.

## D1 / SQL

60. Для новых и измененных запросов к растущим таблицам объясни выбор индексов с учетом условий и сортировки
   и проверь `EXPLAIN QUERY PLAN` на тестовой базе. Полный просмотр таблицы требует объяснения, но не запрещен
   автоматически; не добавляй индекс только ради формального соблюдения правила.
61. Запрещен N+1: SQL-запросы внутри цикла по строкам. Используй `IN (...)`, `JOIN`, batch-запрос
   или предварительную выборку.
62. Один пользовательский сценарий (нажатие кнопки, сообщение, запрос страницы) — обычно не более 2–3 запросов
   к D1. Вкладка «Сегодня» собирается одним запросом к API. Если нужно больше — явный комментарий
   `// QUERY BUDGET EXCEPTION` с короткой подписью (какие запросы) и объяснение в PR.
63. Несколько изменений, которые должны пройти вместе («отметить и записать событие», «перенести и увеличить
   счетчик», «создать план дня»), — одним `batch()`.
64. Не читай одну и ту же строку/настройку несколько раз в рамках одного запроса и не читай из БД запись,
   которая была только что записана и уже доступна в памяти.
65. Статус задачи не хранится, а вычисляется (архив / пауза / «можно сейчас»); приоритет вычисляется из четырех
   меток. Не добавлять для них отдельных колонок-копий.
66. Любая таблица, которая может бесконечно расти, должна иметь правило очистки со сроком из спецификации;
   если его еще нет, это отдельная задача, а не блокер текущей.
67. Любое изменение схемы или индексов — только новой миграцией. Уже примененные файлы миграций не менять.
   Схема описывается в Drizzle, миграции применяются через `wrangler d1 migrations`. Обычный SQL без
   особенностей D1, кроме `batch()`, чтобы переезд на PostgreSQL оставался возможным.
68. Любой `LIKE '%...%'` с пользовательским текстом экранирует `%`, `_`, `\` и укладывается в лимит D1
   на шаблон LIKE/GLOB — 50 байт вместе с `%` и экранированием (русские буквы занимают больше одного байта,
   поэтому обрезать по числу символов нельзя).

## Повторное использование

69. Перед созданием функции найди существующую реализацию.
70. Общие операции — только через существующие сервисы/хелперы. Новая копия существующей логики запрещена
   без объяснения в PR.
71. Не добавляй неиспользуемые экспорты, типы, функции, поля и импорты.

## Комментарии в коде

72. Комментарий объясняет только, что код делает. Все «почему» (почему решено так, а не иначе, обходы особенностей
   Telegram/D1/Workers/MCP/OAuth, почему проверка или порядок операций именно такие) записываются
   в `docs/decisions.md`, а не в код. Исключения: метка `QUERY BUDGET EXCEPTION` с короткой подписью и короткое
   предупреждение «не менять» с объяснением, без ссылки на `docs/decisions.md`, там, где очевидная правка сломает
   поведение (порядок операций, `void` и т.п.).
   Не писать в комментариях даты, «решение DD.MM», номера PR, номера пунктов ревью/обсуждения/плана,
   упоминания ревьюеров (CodeRabbit, Sourcery и т.п.) и «раньше было/было заменено на».
   Имя владелицы не должно встречаться в комментариях и строках кода вообще.

## Перед завершением задачи

73. Перечислить новые/измененные SQL-запросы с указанием индексов.
74. Указать число запросов к D1 и вызовов Telegram в основном сценарии задачи.
75. Проверить, нет ли N+1, лишних чтений и дублей, нет ли SQL вне `src/db` и чисел правил вне настроек.
76. Запустить `npm run typecheck` и `npm test` (Vitest + `@cloudflare/vitest-pool-workers`): тесты прав,
   выбора дня и совпадения ключей i18n обязательны.
77. Если какое-то правило нарушено — остановиться и спросить, а не делать обходное решение.
78. Задача (включая ревью/проверку по списку пунктов) выполняется полностью, без самовольного урезания
   объема ради экономии времени/усилий — если нужно сократить, сначала спросить.

## Перед merge

79. Прочитать все комментарии и ревью на PR (включая ботов) и ответить на них — фикс в коде или объяснение,
   почему не фиксится — прежде, чем предлагать merge.
80. GitHub Actions (тесты, typecheck, gitleaks) должны быть зелеными на последнем коммите PR.
   Красные — не сливать, сначала починить.
81. Проверить, не занят ли номер новой миграции другим открытым PR; если занят — переименовать свою.

## После merge (команды для владелицы)

82. Выполняются на машине владелицы, не в контейнере агента.

83. Каждый блок команд начинается с `cd ~/YouMustHaveBeen/taskbuddy`. Перед деплоем и применением
   миграций — `git checkout main` и `git pull` в том же блоке: локальная копия сама не обновляется,
   и устаревший деплой или «No migrations to apply!» обычно именно из-за этого.
84. Wrangler вызывается через `npx wrangler ...` (в PATH его нет). Миграции — `npx wrangler d1 migrations
   apply taskbuddy --remote`, деплой — `npx wrangler deploy`.
85. Если wrangler падает с `7403 "account is not valid or is not authorized"` при правильном аккаунте
   в `whoami` — это протухший локальный OAuth-токен: `npx wrangler logout`, затем отдельной командой
   `npx wrangler login` (откроет браузер), затем повторить команду.
86. Секреты (`TELEGRAM_BOT_TOKEN`, `WEBHOOK_SECRET` и другие) задаются через `npx wrangler secret put`, а не
   хранятся в файлах репозитория.
87. Команда с интерактивным вопросом y/n дается отдельно, остальные команды одной задачи — одним блоком,
   строка за строкой, без `&&`.

## Публикация

88. Разработка идет в приватном репозитории. Для публикации: gitleaks по всей истории, затем `git archive main`
   в новый публичный репозиторий одним коммитом, чтобы pull request'ы и обсуждения туда не попали.
