# Решения по коду TaskBuddy

Здесь записано, почему код устроен именно так, когда причина не видна из самого кода: выбор библиотеки,
необычный порядок операций, сознательный отказ от очевидного решения, исключения из правил AGENTS.md.

Каждое решение — отдельный раздел: что решено, почему и какие места в коде оно затрагивает.
Решения о том, что делает система, лежат в спецификации (`docs/requirements.md`, `docs/architecture.md`),
здесь их не повторяем.

Файл обновляется в том же PR, что и код, к которому относится решение.

## Первая пользовательница — по коду из секрета

На этапе 0 таблицы приглашений еще нет, а новые пользователи появляются только по коду приглашения. Поэтому код
владелицы хранится секретом `OWNER_INVITE_CODE`, и `/start <код>` создает семью и пользователя. Вставка идет
с условием «пользователей еще нет»: пока система для одного пользователя, второй по тому же коду не
зарегистрируется, даже если код утечет. Условная вставка сделана подготовленными запросами D1 в `batch()`, потому
что запрос Drizzle через `sql` внутри `batch()` не выполняется. Код: `src/core/auth.ts`, `src/db/users.ts`.

## Токены хранятся хешем

В `sessions` лежит только SHA-256 токена сессии или ссылки входа, а сам токен знает только клиент. Утечка
базы не дает войти. Одноразовая ссылка из `/web` — строка `sessions` с `kind = login_link`; погашение одним
`UPDATE ... WHERE used_at IS NULL ... RETURNING`, поэтому ссылка срабатывает ровно один раз. Код:
`src/core/auth.ts`, `src/db/sessions.ts`.

## Очистка без cron

Просроченные строки `sessions` и старые `tg_updates` удаляются в том же `batch()`, что и вставка новой строки,
по индексу на срок. Так на этапе 0 не нужны ни cron, ни `jobs`: они появятся с этапа 2а.

## Бот создается на каждое обновление

Объект grammY создается заново для каждого обновления, чтобы обработчики получали базу и адрес Worker
из замыкания. Данные `getMe` кэшируются в памяти isolate, поэтому запрос к Telegram за ними — один раз
на isolate, а не на каждое обновление. Код: `src/telegram/bot.ts`.

## Настройка вебхука из Worker

`POST /tg/setup` с заголовком `X-Setup-Secret` (тот же `WEBHOOK_SECRET`) регистрирует вебхук с секретным
токеном и ставит обычную кнопку меню Telegram (без открытия страницы внутри Telegram). Так токен бота не нужно вводить в терминале, и все вызовы Telegram
остаются в `src/telegram`. Код: `src/telegram/routes.ts`.

## Вход на страницу только по ссылке из бота

Мини-приложения Telegram нет: страница открывается в браузере, вход по одноразовой ссылке. Ссылка приходит
одним словом «TaskBuddy» (HTML-ссылка), адрес и срок в тексте не показываются. Кнопка «Выбрать» в утреннем
сообщении — не кнопка-ссылка, а обычная кнопка: ссылка одноразовая и с ограниченным сроком, а сообщение висит
весь день, поэтому новая ссылка создается при каждом нажатии. В адресе ссылки `&` экранируется как `&amp;`,
потому что сообщение отправляется в режиме HTML. Код: `sendLoginLink` в `src/telegram/day.ts`.

## Telegram ID в core

`telegram_id` — поле пользователя по схеме, поэтому core ищет пользователя по нему. Все, что относится
к самому Telegram (grammY, вебхук), лежит в `src/telegram`.

## Поля пользователя по этапам

В `users` на этапе 0 только то, что нужно для входа: семья, Telegram ID, имя, язык, часовой пояс.
Время опроса, день обзора и `now_block` добавляются миграциями своих этапов. Колонки роли нет: роль одна.

## Дата совместимости Worker

`compatibility_date = 2026-08-20`: последняя версия `@cloudflare/vitest-pool-workers` несет среду Workers,
которая знает даты только до 2026-08-22. Пакет переименован в `@cloudflare/vitest-plugin` и больше
не обновляется (см. `docs/pending.md`).

## Справочники у каждого пользователя свои и пустые

Сферы, виды действий, категории и награды лежат с `user_id`, а не в общем списке: «дом» и «домашнее» разные значения
у разных людей. Заранее ничего не создается, список заполняет пользователь. Названия сфер, видов действий и категорий
уникальны в пределах пользователя (регистр различается); у наград названия могут повторяться. Код: `src/db/schema.ts`, `src/db/references.ts`.

## Удаление значения справочника

Значение, на которое ссылается запись, удалить нельзя: внешний ключ D1 отклоняет запрос, а слой доступа превращает
это в ответ `in_use` (по тексту ошибки D1, другого признака у нее нет). Пары совместимости категорий
при удалении категории удаляются тем же `batch()`. Код: `src/db/references.ts`.

## Совместимость категорий хранится парой в одном порядке

Пара `(A, B)` и `(B, A)` — одна и та же, поэтому `core` упорядочивает идентификаторы перед записью, а первичный
ключ не пускает дубль. Категория не совместима сама с собой. Код: `src/core/references.ts`.

## Список справочников одним batch

Вкладка «Справочники» получает пять списков одним запросом к API и одним `batch()` к D1 вместо пяти обращений.
Это исключение из бюджета запросов (`QUERY BUDGET EXCEPTION` в `src/db/references.ts`).

## Метки приоритета в базе могут быть пустыми

Четыре метки приоритета в `tasks` могут быть пустыми: у записи из бота или импорта карточки еще нет, пустое значение считается «нет» (см. «Метки приоритета — квадратики с галочкой»). Задачей запись становится только по кнопке «Добавить» (когда обязательные поля заполнены), а до этого у нее `kind = inbox`. Приоритет и статус
по-прежнему вычисляются, колонок для них нет.

## Метка «очередь» отдельной колонкой

В «Архитектуре» у очереди только `queued_after_id`, но «Требования» разрешают ставить метку вручную без указания,
после какой задачи. Поэтому добавлена колонка `queued`, а `queued_after_id` остается для автоматической очереди
в проекте.

## Карточка: сохранение по полям, переход записи в SQL

Каждое поле карточки уходит на сервер сразу при изменении (`PATCH /api/items/:id`, только известные поля); текстовые поля сохраняются, когда пользователь уходит из поля, а выборы и отметки сразу. Вид записи
сохранением не меняется: запись уходит из инбокса только кнопкой «Добавить» (`POST /api/items/:id/promote` с типом `task` или `project`; тип выбирается в списке «Что это?» и хранится на странице до нажатия, признак проекта `is_project` ставится тем же переводом, отдельной галочки нет), которая работает, когда обязательные поля заполнены, иначе 409. Переход делает одно условное `UPDATE` в SQL. Условие «обязательные поля заполнены» записано дважды: в
`missingFields` (`src/core/items.ts`, для подсказки на странице) и в `completeSql` (`src/db/items.ts`); тест проверяет
оба случая. Если очистить обязательное поле у уже добавленной задачи, она остается задачей. Кнопка «Добавить» делает один `batch()` из шести запросов (строка задачи только у записей вида инбокс и задача, условный перевод признака проекта и вида с проверкой «владелица или автор» и «не в архиве», чтение записи, задачи и сфер): исключение из бюджета запросов (`QUERY BUDGET EXCEPTION` в `promoteCard`), зато проверка доступа и перевод атомарны. Сфер у записи не больше трех (`itemMaxSpheres`). Сферы, вид,
категория и проект берутся только из справочников владелицы записи (проверка отдельным `batch()`, это один из
двух-трех обходов D1 на сохранение).

## Метки приоритета — квадратики с галочкой

Четыре метки приоритета в карточке — квадратики: галочка значит «да», пустой квадратик — «нет». Отдельного состояния «не выбрано» нет, поэтому метки не входят в обязательные поля: запись можно добавить задачей, когда заполнены сфера и вид (и «зачем», если стоит «важно» или «эффект»). В базе метки остаются допускающими пустое значение (запись из бота, импорт); пустое считается «нет».

## Даты карточки

Дедлайн, напоминание и «отложено до» хранятся в миллисекундах UTC. Страница переводит дату и время из часового пояса
браузера. Все пользователи живут в Дублине (решение владелицы 27.11.2026), поэтому часовой пояс браузера совпадает с настройкой. Если появится пользователь в другом поясе, перенести расчет на часовой пояс из настроек.

## Инбокс: удалить и запись из бота

«Удалить» в инбоксе переносит запись в архив как неактуальную (`archive_reason = irrelevant`). Запись из бота
сохраняется целиком как название (до 4096 знаков, это предел сообщения Telegram); команды (начинаются с «/») не
сохраняются и остаются без ответа; на обычный текст незнакомого человека бот отвечает, что он закрытый. Подтверждение записи — реакция 👍 на сообщение (`setMessageReaction`), а не ответное сообщение; в `i18n` для нее строки нет.

## Индексы инбокса

Список инбокса: `owner_id = ? AND kind = 'inbox' AND archived_at IS NULL` идет по индексу `items_owner_kind`;
условие «или автор» обслуживает `items_creator`. Новых индексов нет.

## План дня

План дня (`day_plan`) составляется при первом запросе `GET /api/today` за дату пользователя (по его часовому поясу,
`date-fns-tz`) и за день не пересчитывается: следующие запросы только читают его. Строки плана пишутся одним
`batch()` с `INSERT OR IGNORE` по первичному ключу (user_id, date, slot, position), поэтому два одновременных первых
запроса оставляют один план. Пустой план не записывается: пока задач нет, каждый запрос пробует составить его заново.
Условие «утро после пройденного вечернего опроса» добавляется вместе с опросом.

В план идут только задачи, которые пользователь выполняет сам (`owner_id`), не проекты и не шаги проекта в фокусе
или отложенного проекта. Причина паузы (отложено без даты или до будущей даты, в очереди, «жду») считается в core
(`pauseReason` в `src/core/day.ts`), тем же условием, что статус в списке задач.

Блок дедлайнов: задачи со сроком до сегодняшней даты плюс `deadlineHorizonDays` включительно (дата срока считается
в часовом поясе пользователя), по порядку срока, в том числе задачи на паузе: у них в плане есть поле `pause`
(`deferred`, `queued`, `waiting`), страница будет показывать его пометкой (часть 2 этапа 2а). Задачи блока дедлайнов за кнопки не идут.
За каждой из четырех кнопок одна задача «можно сейчас» с этой отметкой, без повторов в плане и без «дофамина». Задача выбирается случайно с весом
(1 + баллы приоритета) × (1 + дней с последнего показа, не больше `pickStaleDaysCap`) × (`pickFrogBoost` для лягушки);
никогда не показанная считается показанной `pickStaleDaysCap` дней назад. Время показа (`last_shown_at`) пишется,
когда пользователь нажал кнопку и увидел задачу (часть 2 этапа 2а), а не при составлении плана: задачи за ненажатыми
кнопками показанными не считаются. Если задач с отметкой нет, берется задача
с наибольшим приоритетом (при равенстве с важностью или эффектом, затем дольше не показанная). Случайность передается
в core параметром, чтобы тесты были детерминированными.

Строки четырех кнопок пишутся скрытыми (`hidden`): задача видна после нажатия кнопки, тогда же пишется
`last_shown_at`.

## Действия плана дня

`POST /api/today/:slot/:position/:action` меняет одну строку плана и в том же `batch()` читает план заново.
Первая запись batch проверяет, что строка в ожидаемом состоянии; остальные записи идут с условием
`changes() > 0`, поэтому повторное нажатие или параллельный запрос ничего не делают и получают 400. Новые строки
(замена, «Обновить», «Дофамин») пишутся на позицию + 1 того же слота через `INSERT OR IGNORE`; текущая задача
кнопки — строка с наибольшей позицией. Переходы: `offered` → `accepted` | `refused`; `refused` → `accepted`
(«Все же взять») или завершение отказа (`next`): счетчик отказов `skip_count` + 1, ответ «Что мешает?» в `insights`,
замена той же отметки, пока замен меньше `refusalReplacements`, иначе `closed`; `accepted` → `done` (задача в архив
как выполненная). Дофаминовая задача: «Пропустить» и «Закрыть» переводят ее в `closed` без счета отказа и без
архива. «Что мешает?» спрашивается и счетчик неудач растет не чаще раза на задачу в день: день последней неудачи
хранится в `tasks.last_fail_on`. «Выбрать»
(`POST /api/today/pick`) добавляет строку `picked` сразу принятой; задача, которая сегодня уже была в плане в любом
состоянии (в том числе после отказа), второй раз не берется — условие `NOT EXISTS` в самой вставке; при пустом плане
он сначала составляется без выбранной задачи, чтобы она не оказалась за кнопкой. Кольцо: выполненные задачи всех слотов, кроме
дедлайнов, из `dayRingTasks`.

Планы хранятся `dayPlanKeepDays` дней; удаляет старые ночная задача.

## Вечерний опрос

Опрос не хранится отдельно: в нем принятые несделанные строки плана (`state = 'accepted'`, задача не в архиве)
прошлых дней, а с `surveyAt` и сегодняшние. План дня читается одним запросом вместе с такими строками прошлых дней
(диапазон по первичному ключу `day_plan`), поэтому «Сегодня» по-прежнему один запрос. Если есть строка прошлого
дня, опрос не пройден: план на сегодня не составляется и кнопки не показываются. Ответ меняет состояние строки на
`tomorrow`, `returned` или `dropped`. «На завтра» вставляет строку `picked` в план следующего дня (но не раньше
сегодняшнего, если опрос проходят на следующий день); план с одними перенесенными строками считается
несоставленным и дописывается кнопками и дедлайнами без них. Последний ответ, открывающий день, сразу составляет
план.

Неудача (отказ, «На завтра», «В хранилище») в одном batch: `skip_count` + 1, если `last_fail_on` не этот день; при
пороге `frogThreshold` задача без отметки становится лягушкой (`frog_auto = 1`), создается задача «Подумай, почему
откладываешь: название» и встает строкой `think` в план следующего дня. Эти записи цепляются друг за друга через
`changes()`. Проверка состояния строки плана здесь последняя: перед ней идут записи, которые могут ничего не
изменить (неудача уже была сегодня), и они сами проверяют условие ожидания через `EXISTS`, а `changed` берется
у последней записи. Batch D1 — одна транзакция, поэтому повторное нажатие ничего не пишет.

## Расписание без таблицы jobs

Cron раз в 5 минут. Таблицы jobs нет: при правке «Напомнить» в карточке не нужно синхронизировать вторую таблицу.
События дня (ночь, утро, дедлайны, опрос) отмечаются датой в `users` (`survey_on`, `morning_on`, `reprompt_on`,
`deadline_on`, `night_on`) одним `UPDATE ... WHERE отметка < сегодня RETURNING`: событие берет ровно один запуск
или одно действие пользователя. Отметка ставится до отправки; если Telegram ответил ошибкой, она возвращается
к прежнему значению (только если ее с тех пор не меняли), и через 5 минут событие отправляется снова. Так же
возвращается снятое напоминание и вопрос бота, ответ на который не удалось обработать. Пока опрос не пройден, утром
один раз (`reprompt_on`) приходит «Сначала вчерашний опрос»; отдельного вечернего опроса в тот же запуск нет.
Если Worker оборвется между захватом и отправкой (без ошибки), событие за этот день теряется; отметку
«отправляется» со сроком решено не заводить: обрыв редкий, теряется не больше одного сообщения в день.
Утро и длинный список дедлайнов — несколько сообщений; если не ушло одно из следующих, повтор пришлет и уже
отправленные (лишнее сообщение, ничего не теряется). Если ночью Telegram не дал удалить старый вопрос бота,
второй попытки нет: сообщения старше двух суток бот удалить не может, вопрос можно удалить вручную. Пройденный в боте опрос после `morningAt` сам берет
отметку утра и присылает кнопки; пройденный на странице — ближайший запуск расписания. Напоминания читаются по
индексу `tasks_remind_at` и снимаются `UPDATE ... RETURNING`; архивные и не задачи снимаются без отправки.
Запуск без событий — один batch из двух чтений (пользователи и наступившие напоминания).

## Бот: карточки, вопросы и список

В `callback_data` (до 64 байт) записаны дата и строка плана: `b|дата|слот` (кнопка), `d|дата|слот|позиция|действие`,
`s|дата|слот|позиция|ответ[|k]` (опрос, `k` — «Пропустить» на «Что мешает?»), `r|t|id` и `r|a|id|время`
(напоминание), `l|дата|слот|позиция` («Сделано» под списком). Кнопка напоминания, которая не сработала (задачу
удалили), снимается с пометкой «Это уже изменилось»; «Взять сегодня» при непройденном вчерашнем опросе присылает
сначала опрос и задачу не добавляет. Кнопка с датой не сегодняшнего дня показывает актуальное состояние, а не действует на сегодняшнюю
строку с той же позицией. Шаги отказа в боте (`wr` — записать причину, `sw` — пропустить «зачем», `sb` —
пропустить «Что мешает?») живут только в боте; на сервере это те же действия `reason` и `next`.

Причина отказа и «Что мешает?» — ответом на сообщение бота (`force_reply`). У сообщения с `force_reply` не может
быть инлайн-кнопок, поэтому «Пропустить» стоит на карточке, а контекст вопроса (строка плана, сообщение карточки)
хранится в `bot_prompts` по номеру сообщения вопроса. Ответ не на вопрос бота уходит в инбокс, как обычный текст.
При «Пропустить» вопрос удаляется из чата и из таблицы. Невостребованные вопросы ночная задача удаляет из таблицы и из чата.
Ответ на вопрос о причине отказа, присланный уже в другой день, не записывается: карточка показывает актуальное состояние.
Вопрос, который не удалось записать в `bot_prompts`, удаляется из чата: иначе ответ на него ушел бы в инбокс.

Список на сегодня — обычное сообщение; его номер в `users.list_message_id`, старое сообщение удаляется перед
отправкой нового, чтобы список был последним в чате. Под списком кнопки «Сделано: название» для принятых
несделанных задач. Два одновременных изменения могут оставить в чате два списка; следующее изменение это исправляет.

## Вкладка «Задачи»

`GET /api/tasks` отдает все неархивные задачи пользователя (владелица или автор) с баллами, уровнем приоритета и статусом одним
`batch()` из двух запросов (задачи и их сферы). Условие «владелица или автор» записано как `id IN (… UNION …)`, чтобы
SQLite шел по индексам `items_owner_kind` и `items_creator`, а не по `items_archived_at` (проверено
`EXPLAIN QUERY PLAN`). Фильтры и сортировка (по двум полям) работают на странице по уже загруженному списку; блок
фильтров свернут, чтобы список был виден сразу. Кроме фильтров по статусу, отметке, сфере, виду, категории, проекту
и специфике есть фильтр «Фильтр»: выбирается поле (дедлайн, «Напомнить», «Отложено», «В очереди», «Жду», «Первый
шаг»), и остаются задачи, где оно заполнено, а с флажком «Не заполнено» — где не заполнено. Сортировка — по любому
полю карточки; сферы, вид, категория и проект сортируются по названию, пустые значения в конце.

Карточка задачи та же, что в инбоксе, без списка «Что это?» и кнопки «Добавить». У задачи, которую выполняет
другой человек (пользователь только автор), в списке и в карточке есть пометка «Чья задача: имя» (`ownerName`
в ответе), а сферы, вид, категория и проект в карточке скрыты: справочники у автора свои, а сервер проверяет выбор
по справочникам хозяина задачи.

## Таймер

Таймер хранится в таблице `timers`, одна строка на пользователя (первичный ключ `user_id`): это и есть правило «один
таймер на пользователя». Состояние выводится из колонок: идет, если есть `ends_at`; на паузе, если есть `paused_at`
и `remaining_sec`; остановлен (нажали «Стоп» или время вышло), если обоих нет. Остановленный таймер остается строкой
и ждет одной из четырех кнопок; «Продолжить позже» и «Сделано» строку удаляют. Новый таймер записывается одним
`INSERT … ON CONFLICT (user_id) DO UPDATE … WHERE`: он заменяет только остановленный таймер, таймер с вышедшим
временем (будильник мог еще не сработать) или таймер задачи, ушедшей в архив; идущий или стоящий на паузе таймер
не заменяется, и ответ — «Уже идет таймер». У `timers.item_id` нет внешнего ключа на `items`: таймер бывает у задачи, зоны
или награды (`kind`); сейчас он запускается у задач и наград, таймер зоны — на этапе 3. Таймер, задача которого
ушла в архив или награда удалена, не читается (`LEFT JOIN` на `items` и `rewards` по `kind`) и заменяется следующим
запуском.

Окончание — alarm Durable Object `TimerAlarm` (один объект на пользователя, `idFromName(user_id)`), а не cron.
Будильник ставится при запуске и при «Продолжить» после паузы; пауза и «Стоп» его не снимают: сработав раньше,
будильник видит, что время не вышло, и ничего не делает. Таймер, время которого вышло, везде считается
остановленным, даже если будильник еще не сработал: «Пауза» не принимается, доступны четыре кнопки. Сработав,
будильник у таймера из бота сначала присылает новое «Время вышло» с четырьмя кнопками, а затем одним `UPDATE`
останавливает таймер и записывает номер сообщения; прежнее сообщение таймера удаляется. Если отправка не удалась,
в базе ничего не меняется и ошибка в `alarm()` запускает повтор будильника. `UPDATE` срабатывает, только если
`ends_at` тот же, что видел будильник: если таймер за это время продолжили или запустили заново, он не меняется,
а лишнее сообщение удаляется. Второе «Время вышло» возможно, только если Telegram сообщение принял, а запись
в базу не удалась. Таймер, запущенный на странице, в боте не показывается и только останавливается; страница
считает мм:сс сама и в конце играет звук. «Уже идет таймер» в боте у таймера со страницы приходит без кнопок таймера.

Кнопки таймера в боте действуют только на сообщении, номер которого записан в `timers.bot_message_id`; на старом
сообщении кнопки устарели. Если таймер из бота меняют на странице, сообщение бота меняется в фоне (`waitUntil`).
«Парковка» в боте — вопрос с ответом на сообщение (`bot_prompts.kind = park`), ответ уходит в инбокс с 👍.

## Награды и первый шаг

Список на сегодня — награда, задача, награда … и в конце награда: на N задач списка N + 1 награда. Места наград
не хранятся строками плана дня: строка `day_plan` обязана указывать на задачу (`item_id` с внешним ключом на `items`),
а награды лежат в `rewards`. Выбранная на место награда записывается в `day_rewards` (первичный ключ
`user_id, date, position`; внешний ключ на `rewards` с `ON DELETE CASCADE` и индекс `day_rewards_reward` для него).
Награды пользователя и выбранные места читаются вторым запросом в том же `batch()`, что и план дня, поэтому число
обращений к D1 не растет. Сделанные задачи в списке идут первыми; открыта награда на месте «число сделанных», то есть
перед первой несделанной. Награда открытому месту выбирается случайно в момент, когда место открылось (при первом
чтении плана после этого), и записывается `INSERT OR IGNORE`: два одновременных чтения оставят один выбор.
Прошедшие места показывают свою награду, следующие скрыты. Без задач или без наград список наград пустой, и кнопки
«Награда» нет. Кнопка «Награда» после «Сделано» показывает ту же открытую награду. Таймер награды идет на ее длину
из «Справочников», без «Парковки»; после конца у него одна кнопка «Завершить», которая снимает таймер.
Старые места наград удаляет ночная очистка вместе с планом дня. Прошедшее место без награды (наград тогда
не было или награду удалили) не показывается.

Исключение из правила «значение справочника, которое используется, удалить нельзя»: награду можно удалить, даже
если она выбрана в списке на сегодня. Выбранная награда — не запись: `ON DELETE CASCADE` освобождает ее место,
и открытое место получает другую награду. Иначе награду нельзя было бы удалить 30 дней, пока хранится план дня.

Голосовой первый шаг — `tasks.first_step_voice_id` (file_id Telegram, без расшифровки). Вопрос о первом шаге и
сообщение с голосовым — вопросы бота `bot_prompts.kind = first_step`, задача в `action`. Голосовое ответом на них
записывается в задачу; текст ответом на них уходит в инбокс, а вопрос остается, потому что первый шаг в боте только
голосом. Голосовое не ответом на такой вопрос не записывается, бот отвечает подсказкой. Вопрос и голосовое приходят
до списка на сегодня, чтобы список остался последним сообщением. Странице file_id не отдается, только `hasVoice`.
Панель «👁» показывает задачи за кнопками без показа (`hidden` не снимается, `last_shown_at` не меняется) и пишет
текстовый первый шаг через обычное сохранение карточки (`PATCH /items/:id`).

Действия над строкой плана, после которых задача больше не ждет работы («Сделано», «Вернуть», «Закрыть», ответ
опроса), в том же `batch()` удаляют таймер этой задачи. «Вернуть» после таймера — неудача, как «В хранилище» в опросе:
счетчик лягушки, «Что мешает?» (если сегодня по задаче еще не спрашивали), замена за кнопкой в пределах двух замен;
у дофаминовой задачи «Вернуть» — то же, что «Закрыть».
