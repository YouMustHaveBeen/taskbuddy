# Решения по коду TaskBuddy

Здесь записано, почему код устроен именно так, когда причина не видна из самого кода: выбор библиотеки,
необычный порядок операций, сознательный отказ от очевидного решения, исключения из правил AGENTS.md.

Каждое решение — отдельный раздел: что решено, почему и какие места в коде оно затрагивает.
Решения о том, что делает система, лежат в спецификации (`docs/requirements.md`, `docs/architecture.md`),
здесь их не повторяем.

Файл обновляется в том же PR, что и код, к которому относится решение.

## Первая пользовательница — по коду из секрета

На этапе 0 таблицы приглашений еще нет, а новые пользователи появляются только по коду приглашения. Поэтому код
владелицы хранится секретом `OWNER_INVITE_CODE`, и `/start <код>` создает семью и пользователя. Вставка идет
с условием «пользователей еще нет»: пока система для одного пользователя, второй по тому же коду не
зарегистрируется, даже если код утечет. Условная вставка сделана подготовленными запросами D1 в `batch()`, потому
что запрос Drizzle через `sql` внутри `batch()` не выполняется. Код: `src/core/auth.ts`, `src/db/users.ts`.

## Токены хранятся хешем

В `sessions` лежит только SHA-256 токена сессии или ссылки входа, а сам токен знает только клиент. Утечка
базы не дает войти. Одноразовая ссылка из `/web` — строка `sessions` с `kind = login_link`; погашение одним
`UPDATE ... WHERE used_at IS NULL ... RETURNING`, поэтому ссылка срабатывает ровно один раз. Код:
`src/core/auth.ts`, `src/db/sessions.ts`.

## Очистка без cron

Просроченные строки `sessions` и старые `tg_updates` удаляются в том же `batch()`, что и вставка новой строки,
по индексу на срок. Так на этапе 0 не нужны ни cron, ни `jobs`: они появятся с этапа 2а.

## Бот создается на каждое обновление

Объект grammY создается заново для каждого обновления, чтобы обработчики получали базу и адрес Worker
из замыкания. Данные `getMe` кэшируются в памяти isolate, поэтому запрос к Telegram за ними — один раз
на isolate, а не на каждое обновление. Код: `src/telegram/bot.ts`.

## Настройка вебхука из Worker

`POST /tg/setup` с заголовком `X-Setup-Secret` (тот же `WEBHOOK_SECRET`) регистрирует вебхук с секретным
токеном и кнопку меню мини-приложения. Так токен бота не нужно вводить в терминале, и все вызовы Telegram
остаются в `src/telegram`. Код: `src/telegram/routes.ts`.

## Telegram ID в core

`telegram_id` — поле пользователя по схеме, поэтому core ищет пользователя по нему. Все, что относится
к самому Telegram (подпись initData, grammY, вебхук), лежит в `src/telegram`.

## Поля пользователя по этапам

В `users` на этапе 0 только то, что нужно для входа: семья, Telegram ID, имя, язык, часовой пояс.
Время опроса, день обзора и `now_block` добавляются миграциями своих этапов. Колонки роли нет: роль одна.

## Дата совместимости Worker

`compatibility_date = 2026-08-20`: последняя версия `@cloudflare/vitest-pool-workers` несет среду Workers,
которая знает даты только до 2026-08-22. Пакет переименован в `@cloudflare/vitest-plugin` и больше
не обновляется (см. `docs/pending.md`).

## Справочники у каждого пользователя свои и пустые

Сферы, виды действий, категории и награды лежат с `user_id`, а не в общем списке: «дом» и «домашнее» разные значения
у разных людей. Заранее ничего не создается, список заполняет пользователь. Названия сфер, видов действий и категорий
уникальны в пределах пользователя (регистр различается); у наград названия могут повторяться. Код: `src/db/schema.ts`, `src/db/references.ts`.

## Удаление значения справочника

Значение, на которое ссылается запись, удалить нельзя: внешний ключ D1 отклоняет запрос, а слой доступа превращает
это в ответ `in_use` (по тексту ошибки D1, другого признака у нее нет). Пары совместимости категорий
при удалении категории удаляются тем же `batch()`. Код: `src/db/references.ts`.

## Совместимость категорий хранится парой в одном порядке

Пара `(A, B)` и `(B, A)` — одна и та же, поэтому `core` упорядочивает идентификаторы перед записью, а первичный
ключ не пускает дубль. Категория не совместима сама с собой. Код: `src/core/references.ts`.

## Список справочников одним batch

Вкладка «Справочники» получает пять списков одним запросом к API и одним `batch()` к D1 вместо пяти обращений.
Это исключение из бюджета запросов (`QUERY BUDGET EXCEPTION` в `src/db/references.ts`).

## Все поля карточки нулевые, пока не отмечены

Четыре метки приоритета в `tasks` могут быть пустыми (не отмечено), чтобы хранить черновик карточки: задачей запись
становится, когда заполнено последнее обязательное поле, а до этого у нее `kind = inbox`. Приоритет и статус
по-прежнему вычисляются, колонок для них нет.

## Метка «очередь» отдельной колонкой

В «Архитектуре» у очереди только `queued_after_id`, но «Требования» разрешают ставить метку вручную без указания,
после какой задачи. Поэтому добавлена колонка `queued`, а `queued_after_id` остается для автоматической очереди
в проекте.
