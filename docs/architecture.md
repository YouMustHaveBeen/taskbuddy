# Архитектура TaskBuddy

Nov 26, 2026

Архитектура, которая будет реализована: Cloudflare Workers + D1, один Worker, core со всей логикой, Telegram-бот, мини-приложение, веб и Claude через MCP.

## 1. Оценка ТЗ

Основа: ТЗ, предложения DeepSeek, ChatGPT, Perplexity, Claude (артефакт), AGENTS.md от StreetBuddy, документы [TaskBuddy add-ons](https://claude.ai/artifact/UVGwSifDzeukXdtBGLDYDm) и [Команды Claude для TaskBuddy](https://claude.ai/artifact/5RkxtiteySFvSFagftmDM9). Где add-ons меняют прежнее решение, действует add-ons.

### 1.1. Сильные места

1. ТЗ называет настоящую проблему: не забывание, а уход в интересное вместо нужного. Поэтому вся логика дня (кнопки, лягушка, дофамин, фраза «зачем» при отказе) работает на одну цель, а не просто хранит список.
2. Один вход для всего (инбокс) и разбор потом. Это правильный GTD и снимает трение при добавлении.
3. Бот маленький, списки на странице. Это сразу отсекает главную боль Telegram-ботов: простыни сообщений.
4. owner/creator в схеме с первого дня. Дешево сейчас, дорого потом.
5. Тексты отдельно от кода по языкам. То же самое.
6. Есть механизм самоочистки: архив старше года удаляется, раз в неделю обзор, лягушка ставится автоматически.

### 1.2. Противоречия и решения

1. **Кто разбирает инбокс.** Раздел 2 ТЗ: «входящие бот разбирает позже». Раздел 7: «разбор вручную». Раздел 3: Claude через MCP «разбирает входящие». **Решено (26.11.2026 по add-ons):** окончательный разбор за пользователем, он проверяет и правит. Claude предварительно расставляет параметры и пишет первый шаг: по расписанию в 10:00, 14:00, 18:00 и 22:00 и по команде «разбери инбокс» (п. 6.8). Пока пользователь не подтвердил, это только предложение.
2. **Лягушка: два правила.** Раздел 6: «после суммарно 3 невыполнений/отказов». Раздел 7: «после 3 переносов — лягушка и 6-я задача». **Решено:** один счетчик (отказы + переносы), порог 3; задача «подумай, почему откладываешь» появляется на следующий день после того, как счетчик дошел до 3.
3. **Архив хранится год, по нему учится Claude; прогресс считаем отдельно.** Нужна отдельная таблица дневной статистики.
4. **«Удалить» в вечернем опросе.** **Решено:** «Удалить» = в архив с пометкой «неактуально», настоящее удаление через год, вместе с архивом. Такие задачи не считаются в статистике и прогрессе.
5. **Зоны.** **Решено:** календарная неделя пн–вс, обрезанная границами месяца. Зона 1 = неделя с 1-м числом, зона 5 = неделя с последним, между ними по порядку зоны 2, 3, 4. Пример: октябрь 2025 — 1–5, 6–12, 13–19, 20–26, 27–31. При 6 неделях однодневная крайняя неделя присоединяется к соседней: первая к следующей (март 2026: 1–8, …), последняя к предыдущей (август 2026: …, 24–31); если однодневные обе (ноябрь 2026), присоединяется первая: 1–8, 9–15, 16–22, 23–29, 30. При 4 неделях (февраль, начинающийся с понедельника) зона 5 пропускается.

### 1.3. Приоритет и отказы

1. **Веса.** При простой сумме «легкая и срочная» мелочь равна «важной и влиятельной» задаче. **Решено:** важность и влияние дают по 2 балла, срочность и легкость по 1. Сумма от 0 до 6.
2. **Уровни.** **Решено:** главный 5–6, высокий 4, средний 2–3, низкий 1, нет 0. При равной сумме сначала задачи с важностью или влиянием.
3. **Бесконечный отказ.** **Решено:** на одну кнопку не больше 2 замен, дальше задачу можно взять только через «Выбрать».

### 1.4. Что в ТЗ не описано (решено)

1. Горизонт блока дедлайнов: просроченные + следующие 7 дней.
2. Если задач с нужной меткой нет, кнопка добирается задачей «можно сейчас» с наибольшим приоритетом, которой еще нет в плане, не дофамин.
3. «Отложено» без даты снимается только вручную или на еженедельном обзоре.
4. Все правила с числами и временем — не в коде, а переменные: день обзора (воскресенье), вечерний опрос (21:00), горизонт дедлайнов (7 дней), порог лягушки (3), число замен (2), веса и уровни приоритета, длины таймера (5, 10, 15, 25), таймер награды (10), зоны (15), срок архива (1 год), время запусков Claude (10:00, 14:00, 18:00, 22:00), порог обучения (200), обновление выжимки (раз в месяц). Значения по умолчанию в одном файле настроек, свои можно поменять в настройках; они хранятся в таблице settings (user, ключ, значение). Часовой пояс пользователя, по умолчанию Europe/Dublin.
5. Резервные копии: D1 хранит историю 30 дней (Time Travel) + раз в неделю выгрузка в файл в R2 (хранилище Cloudflare, для такого объема копейки).
6. Выгрузка своих данных и удаление аккаунта — к публикации, в MVP не нужно.
7. Telegram есть у всех членов семьи, отдельного входа для детей нет.

## 2. Главное решение: D1, а не PostgreSQL

Было 2 на 2: DeepSeek и Claude (артефакт) за D1, ChatGPT и Perplexity за PostgreSQL. **Выбрана D1.**

### 2.1. Почему аргументы за PostgreSQL здесь не работают

1. **«В D1 нет транзакций»** (DeepSeek, ChatGPT). Неточно. В D1 есть `batch()`: несколько запросов выполняются атомарно, все или ничего. Нет только «интерактивных» транзакций. Для TaskBuddy этого хватает: «отметить и записать событие», «перенести и увеличить счетчик», «создать план дня».
2. **«Сложные связи, статистика, оконные функции»** (Perplexity). SQLite умеет JOIN, оконные функции, JSON, CTE. Данных у семьи — тысячи строк, не миллионы.
3. **«Row Level Security»** (Perplexity). Worker ходит в базу одним техническим пользователем, и чтобы RLS работал, на каждый запрос надо передавать «кто я». Это та же дисциплина, что и общий слой доступа в коде, только сложнее отлаживать. Слой доступа и тесты прав нужны в любом случае.
4. **`SELECT … FOR UPDATE SKIP LOCKED` против дублей** (Perplexity). В D1 то же делается атомарным `UPDATE ... RETURNING`: событие дня отмечается датой в `users`, наступившее напоминание снимается в `tasks`, и событие берет ровно один запуск (таблицы jobs нет, см. п. 6.7). Если отправка в Telegram не удалась, отметка возвращается к прежнему значению, а напоминание — на место, и следующий запуск отправляет снова.

### 2.2. Почему D1 лучше именно здесь

1. D1 уже знакома по StreetBuddy: миграции, `wrangler`, правила AGENTS.md (индексы, N+1, бюджет запросов) переносятся без изменений.
2. Один поставщик, одна панель, одна учетная запись. С PostgreSQL добавляются Neon или Supabase, Hyperdrive, строка подключения как секрет.
3. Нет сетевой задержки: D1 рядом с Worker, кнопки в Telegram отвечают быстрее.
4. Уже оплачено: D1 входит в тариф Workers Paid.

### 2.3. Цена решения и запасной выход

1. Привязка к Cloudflare. Смягчается Drizzle ORM и обычным SQL без особенностей D1, кроме `batch()`. Переезд на PostgreSQL — новая схема в Drizzle и перенос данных, а не переписывание логики.
2. Когда переезжать: если станет больше десятков семей или понадобится полнотекстовый поиск по-русски уровня PostgreSQL.

## 3. Архитектура

```
Telegram ──► /tg/webhook ─┐
Мини-приложение ─► /api/* ─┤
Веб (тот же React) ► /api/* ┼──► core (вся логика) ──► слой доступа ──► D1
Claude ──► /mcp (OAuth) ───┤
Cron раз в 5 минут ───────┘
```

1. **Один Worker**: вебхук бота, API для страницы, MCP, OAuth, cron и раздача страницы. Один деплой, одна база, одни секреты.
2. **core ничего не знает о Telegram и MCP.** Все правила (выбор дня, лягушки, переносы, права) только в core. Бот, страница и MCP лишь вызывают его.
3. **Слой доступа** — единственное место, где есть SQL. Каждый запрос в нем уже содержит «я владелец или автор». На права — отдельный набор тестов.
4. **Мини-приложение и веб — одна страница** на React. Внутри Telegram она входит через initData, в браузере — через Telegram Login.
5. **Структура репозитория:** один пакет с папками, как в StreetBuddy: `src/core`, `src/db`, `src/telegram`, `src/api`, `src/mcp`, `src/jobs`, `web/`, `i18n/`. Не монорепозиторий из многих пакетов, не отдельные Workers, без Queues: долгой фоновой работы в MVP нет; R2 только для еженедельной резервной копии.

## 4. Стек

1. TypeScript, Cloudflare Workers, **Hono** (маршруты), **grammY** (бот).
2. **D1 + Drizzle ORM**, миграции через `wrangler d1 migrations`.
3. **MCP**: Cloudflare Agents SDK (`McpAgent`) + `workers-oauth-provider` — готовый шаблон Cloudflare для удаленного MCP с OAuth. MCP работает на Durable Objects, токены OAuth хранятся в KV.
4. **Голос:** Whisper нет. Записи голосом — диктовка с клавиатуры (бот получает текст) или голосом в Claude (команда «разгрузи голову»). Первый шаг в боте хранится голосовым без расшифровки; на странице он вводится текстом. Расшифровка Telegram Premium боту недоступна.
5. **Страница**: React + Vite + TanStack Query/Table + Tailwind, `@telegram-apps/sdk` для мини-приложения.
6. **Время**: все хранится в UTC, у пользователя IANA-зона, расчеты через `date-fns-tz`.
7. **Тесты**: Vitest + `@cloudflare/vitest-pool-workers`. Тесты выбора дня и прав — с первого этапа.
8. **Безопасность репозитория**: gitleaks на каждый push в GitHub Actions, секреты только в `wrangler secret`.
9. **Стоимость:** 0 сверх уже оплаченного Workers Paid (5 в месяц). Тариф общий со StreetBuddy, GigBuddy и 4602; по их wrangler.toml конфликтов нет. Следить стоит только за общими 5 ГБ хранилища D1. TaskBuddy — отдельный Worker, отдельная база `taskbuddy`, одно расписание cron раз в 5 минут.

## 5. Схема данных

Основа — **одна общая таблица записей**: разбор инбокса меняет вид записи, а не копирует ее.

### 5.1. Таблицы

| Таблица | Поля и смысл |
| --- | --- |
| households, users | семья; пользователь: Telegram id, имя, язык, часовой пояс, время вечернего опроса, день обзора, роль (взрослый/ребенок), household\_id, now\_block (блок «Сегодня» с галочкой «сейчас»), отметки событий дня (survey\_on, morning\_on, reprompt\_on, deadline\_on, night\_on), list\_message\_id (сообщение со списком на сегодня) |
| items | общая: id, kind (inbox / idea / task / routine / practice), title, owner\_id, creator\_id, household\_id, source (bot / web / mcp), assign\_state (none / pending / accepted / declined), archived\_at, archive\_reason (done / irrelevant), created\_at, updated\_at |
| tasks | тот же id; 4 метки приоритета; priority = 2×важность + 2×влияние + срочность + легкость (0–6, вычисляется); why («зачем», обязательна при важности или влиянии); action\_kind\_id; category\_id; deadline; remind\_at; project\_id; is\_project; step\_pos; parent\_task\_id (после «Разбить»); deferred / deferred\_until; queued (метка «очередь», ставится и вручную), queued\_after\_id; waiting\_for + waiting\_since; flavor (dopamine / frog); frog\_auto; skip\_count; last\_shown\_at (последний показ за кнопкой; при прочих равных берется задача, которую дольше не показывали); first\_step\_voice\_id (голосовое в Telegram); first\_step\_text (текст: вписан на странице или написан Claude); in\_focus (проект в фокусе, для вкладки «Сегодня»; не больше focus\_limit проектов, по умолчанию 3 — настройка пользователя) |

| claude\_profile | выжимка правил пользователя после режима обучения: user, text, built\_at, tasks\_count |

### 5.2. Решения по схеме

1. **Статус задачи не хранится, а вычисляется**: архив, если archived\_at; пауза, если отложено / в очереди / жду; иначе «можно сейчас».
2. **Проект = задача с is\_project.** У проекта все поля задачи; шаги — задачи с project\_id и step\_pos.
3. **Идеи без своей таблицы**: у идеи только сферы.
4. **Инбокс — kind=inbox**: запись в инбоксе еще не задача, у нее нет обязательных полей. Переход inbox ↔ task считает SQL в том же `batch()`, что и сохранение поля (`completeSql`); карточка показывает общую подсказку о заполнении обязательных полей (`missing` из core пока не используется на странице).
5. **Зоны** загружаются из таблицы пользователя (CSV: зона; дело; порядок). Таблица zones: user, номер (1–5), название, текущий круг.

## 6. Логика дня, напоминания, таймеры

### 6.1. «Выдай мне дело»: пять кнопок

1. Утром составляется день: карточка на странице (без привязки ко времени) и сообщение бота в 09:00 (настройка; если опрос пройден позже — сразу после него). Нажимать ничего не нужно. Карточка и сообщение бота появляются, только когда пройден вечерний опрос и отмечены утренние рутины (п. 6.10).
2. Бот дает пять кнопок: «Важная», «Срочная», «Эффектная», «Легкая», «Выбрать». Первые четыре — четыре метки приоритета; «эффектная» — метка «влияние».
3. За каждой из четырех кнопок заранее выбрана одна задача с этой меткой: только «можно сейчас», не «дофамин», не шаги проектов в фокусе и отложенных проектов. Выше шанс у задачи с большим приоритетом, у той, что дольше не показывалась, и у лягушки. Выбор сохраняется в day\_plan и за день не пересчитывается.
4. Нажатие на кнопку = задача взята в работу: пользователь видит ее и принимает или отказывается. При отказе — другая с той же меткой, не больше 2 замен. При отказе от задачи с важностью или влиянием сначала показывается «зачем».
5. «Выбрать» открывает хранилище: задачи по приоритету, сверху фильтры по всем полям карточки; пользователь сам выбирает задачу.
6. Иконка «глаз» открывает все задачи за кнопками: можно пройти по каждой и вписать первый шаг текстом в поле (голосовое записывается только в боте).
7. Кнопка «Категория» заменяет задачи за кнопками на задачи выбранной категории.
8. После завершения задачи на ее месте три кнопки: «Награда» (кубок), «Дофамин» (ракета) и «Обновить» (новая задача с той же меткой).
9. «Принять» не запускает таймер. Принять задачу на завтра нельзя.
10. Блок дедлайнов (просроченные + 7 дней) — отдельно над кнопками. Проект участвует первым незавершенным шагом.
11. В день обзора над кнопками карточка «Еженедельный обзор». Кнопки «Хочу еще» нет: ее заменяют «Выбрать» и «Обновить».

### 6.2. Список на сегодня и награды

1. Список на сегодня = принятые задачи в порядке: награда, задача, награда … и в конце награда. Задачи видны, награды скрыты до своей очереди и выбираются случайно из списка наград пользователя.
2. У награды кнопка «Старт»: таймер на 10 минут.
3. В боте список — обычное сообщение, всегда последнее в ленте: после изменений бот удаляет старое и присылает новое.
4. Разделы страницы на вкладках, кнопки «Все остальное» нет. Кольца прогресса, как в 4602, — на вкладке «Сейчас» (п. 6.10).

### 6.3. Первый шаг

1. При «Принять» бот просит голосовое: самое маленькое действие на первые две минуты.
2. Хранится только голосовое (file\_id в Telegram), без расшифровки. Текстом показывается первый шаг, вписанный на странице или написанный Claude.
3. Когда пользователь потом выбирает задачу, бот сначала проигрывает его голосовое. Дальше пользователь сам решает, нажимать ли «Таймер».

### 6.4. Таймер

1. Только кнопкой «Таймер», длина 5, 10, 15 или 25 минут.
2. Пока идет: «Пауза» (замораживает время, становится «Продолжить»), «Стоп», «Парковка».
3. По «Стоп» или когда время вышло — четыре кнопки: «Завершить», «Продолжить» (снова выбор длины), «Продолжить позже» (задача остается в списке на сегодня), «Вернуть» (в хранилище). Названия кнопок решены, тексты в i18n.
4. Таймер хранится на сервере и виден и на странице, и в боте. Один активный таймер на пользователя. Окончание таймера — точный будильник (alarm в Durable Object), а не проверка cron раз в минуту.

### 6.5. Парковка, «Разбить», «+»

1. «Парковка»: идея уходит в инбокс, текущая задача и таймер продолжаются.
2. «Разбить»: форма с названием проекта и шагами по строкам. Первый шаг остается в списке на сегодня, проект и остальные шаги уходят в инбокс на проверку, все наследуют параметры.
3. «+» открывает полную форму карточки, минуя инбокс: поля сохраняются сразу как черновик, задачей запись становится по кнопке «Добавить», когда заполнены обязательные поля.
4. После записи в инбокс бот ставит на сообщение реакцию-лайк 👍 вместо ответного сообщения.

### 6.6. «Что мешает?» и вечерний опрос

1. Когда задача не сделана (отказ, «на завтра» или «вернуть»), бот спрашивает «Что мешает?», не чаще раза на задачу в день; вопрос можно пропустить. Ответ в insights, только текст.
2. В 21:00 по каждой несделанной: «на завтра / в хранилище / удалить»; перенос и отказ увеличивают skip\_count (не больше одной неудачи на задачу в день), на 3 — лягушка и задача «подумай, почему откладываешь» шестой задачей (слот think) в плане следующего дня. День последней неудачи — tasks.last\_fail\_on. В опросе только принятые несделанные задачи; если их нет, опрос пройден и бот молчит. «На завтра» ставит задачу принятой (слот picked) в план следующего дня, а составление плана дописывает кнопки без нее. Опрос показывается и на странице.
3. Если опрос не пройден, в 09:00 вместо кнопок приходит «Сначала вчерашний опрос» и опрос, после него — пять кнопок и список; план дня не составляется, пока опрос не пройден.
4. В боте причина отказа и «Что мешает?» — ответом на сообщение бота (force\_reply); контекст вопроса хранится в bot\_prompts.

### 6.7. Расписание

1. Cron раз в 5 минут. Событие дня (опрос, утро, дедлайны, ночь) отмечается датой в users одним `UPDATE ... WHERE отметка < сегодня RETURNING`, поэтому его берет ровно один запуск. Напоминания — по remind\_at (индекс), снимаются `UPDATE ... RETURNING`. Если отправка не удалась, отметка и напоминание возвращаются, и следующий запуск отправляет снова. Таблицы jobs нет.
2. Утро (сообщение бота в 09:00 — после вечернего опроса, с этапа 3 и после отметки утренних рутин) и зона дня; напоминания по remind\_at (кнопки «Взять сегодня» и «Напомнить снова завтра») и накануне дедлайна в 10:00; 21:00 опрос. Все время — настройки, по поясу пользователя.
3. Ночью (03:00): удалить планы дня старше 30 дней и вопросы бота старше суток, снять истекшие «отложено»; удалить архив старше года и записать daily\_stats — вместе со статистикой.

### 6.8. Claude разбирает инбокс

1. Делает Claude по подписке, а не бот: запланированная задача в Claude в 10:00, 14:00, 18:00 и 22:00 (время — настройка) заходит в TaskBuddy через MCP. Сначала дешевая проверка, есть ли новое; если нет, запуск сразу заканчивается. Если Claude не заходил больше суток, бот присылает оповещение. Помощь Claude получает только владелец подписки, члены семьи ее не получают. При запусках по расписанию Claude только читает и предлагает параметры и первый шаг (inbox\_suggest), статусы не меняет и ничего не удаляет; команды владельца в чате работают с его обычными правами. Вызовы через API были бы платными. Задача создается без папки: по справке Claude такие задачи идут на всех платных тарифах, даже когда компьютер спит; включенный компьютер нужен только задачам с папкой. У владелицы компьютер ночью и так включен. Это не гарантия: про пропущенные запуски справка молчит, пропуски проверяем на этапе 6.
2. Параметры и первый шаг Claude предлагает с первого запуска, по общим правилам.
3. На 200 — один раз режим обучения: Claude читает разобранные задачи, сохраняет короткую выжимку правил в claude\_profile; дальше читает только выжимку и новые записи и по ним уточняет правила. Выжимка обновляется раз в месяц.
4. Для каждой записи инбокса Claude сохраняет предложение в suggestions: параметры и первый шаг. Пользователь правит и подтверждает.
5. Команды в чате: «Разгрузи голову» (поток → отдельные записи в инбокс без параметров) и «Разбери инбокс» (то же, что запуск по расписанию, но сразу).

### 6.9. Не реализуем сейчас

1. Поле «где я остановилась» в карточке проекта — на будущее.
2. «Сфера месяца» — на будущее.
3. Интерфейс (палитра, крупные кнопки, простой режим) — после первой версии.
4. Интеграция с Alexa — только в документе «Идеи».

### 6.10. Веб-страница

1. Вкладки сверху, по порядку: «Сейчас», «Сегодня», «Инбокс», «Задачи», «Проекты», «Практики», «Рутины», «Идеи», «Инсайты», «Справочники». Вкладки заменяют кнопку «Все остальное». У каждой свой запрос к /api, данные дает core. Мини-приложение и веб — одна и та же страница.
2. «Сегодня» собирается одним запросом. Блок рутин: рутины дня по routines.part\_of\_day (утро, день, вечер) с отметками из routine\_marks за сегодня.
3. Блок FlyLady: название зоны текущей недели (по правилу зон) и 10 дел этой зоны, начиная с первого неотмеченного в текущем круге (routines.order + routine\_marks); кнопка таймера на 15 минут (timers.kind = zone). Число 10 — переменная.
4. Блок практик: все практики пользователя; те, что выполнены по practice\_logs, показываются как выполненные.
5. Блок пяти задач: задачи из day\_plan на сегодня.
6. Блок «проекты в фокусе»: проекты с in\_focus, название и три первых несделанных шага по step\_pos, включая шаги в очереди.
7. Галочка «сейчас»: users.now\_block хранит один активный блок; поставить галочку на блок = записать его в now\_block, прежний снимается сам.
8. «Сейчас» показывает блок из now\_block. Над ним в ряд кольца по всем блокам «Сегодня», кольцо активного в 1,5 раза больше. Если галочку не ставили: до отметки утренних рутин активен блок утренних рутин, после — пять задач; если утренних рутин нет — сразу пять задач. Прогресс считает core: рутины — по доле отмеченных дел, FlyLady — да/нет (полное, когда отработаны 15 минут таймера зоны), пять задач — 20% за задачу, проекты — да/нет по project\_marks, практики — по минимуму на день (100%, если дневной минимум выполнен; практики с суммарной целью тоже по дневному минимуму).
9. «Проекты»: список проектов; при клике справа кнопки «В фокус» (in\_focus, не больше focus\_limit), «Отложить» (deferred, как у задачи), «Разбить»; у проекта в фокусе — отметка «выполнен на сегодня» (project\_marks).
10. «Инсайты» — список из insights со сферами.
11. Утро: карточка на странице и сообщение бота появляются, только когда пройден вечерний опрос и отмечены утренние рутины; сообщение бота — в 09:00 или сразу после опроса, если он пройден позже. Кнопка «Утренние рутины сделаны» — один batch в routine\_marks; после нее карточка и сообщение появляются сразу. Если не отмечены, бот молчит. Если утренних рутин у пользователя нет, задачи приходят после опроса.
12. Мгновенное сохранение: выбор из выпадающего списка и ввод в поле сохраняются сразу (запрос на каждое изменение, ввод — после паузы в наборе), кнопки «Сохранить» нет. Незаполненная карточка и форма «+» хранятся черновиком; задачей запись становится по кнопке «Добавить», когда заполнены обязательные поля.
13. «Справочники»: списки сфер, видов, категорий и наград, раздел «Параллельно» (пары совместимых категорий). Значения добавляются, переименовываются и удаляются; значение, которое используется в записях, удалить нельзя. Одним запросом к API приходят все пять списков.

## 7. Доступ, семья, языки

1. **Бот**: проверка секретного токена вебхука; защита от повторов Telegram по update\_id; новые пользователи только по коду приглашения (как закрытая группа в StreetBuddy).
2. **Мини-приложение**: проверка подписи initData на сервере, затем короткий токен сессии.
3. **Веб в браузере**: Telegram Login или одноразовая ссылка по команде /web в боте (Claude (артефакт)). Ссылка проще: не нужно настраивать домен виджета.
4. **MCP**: OAuth 2.1, вход внутри OAuth через ту же одноразовую ссылку из бота. Пользователь берется из токена, а не из того, что прислал Claude (ChatGPT).
5. **Права** — в слое доступа: видишь, если ты владелец или автор. Поручение: автор создает запись с owner = получатель и assign\_state = pending; получатель принимает или отклоняет; пока не принято, автор может изменить или отозвать. При отказе автору приходит сообщение об отказе. Обязательные поля поручения не заполнены. Ребенок ничем не отличается от взрослого: одна роль, без отдельных правил.
6. **Языки**: `i18n/ru.json` и `i18n/en.json`, `Intl.PluralRules` для склонений, тест на совпадение ключей. Язык при первом входе берется из Telegram, потом меняется в настройках. Названия рутин и задач пользователь пишет сам и не переводятся.

## 8. MCP-инструменты

1. inbox\_add (для «Разгрузи голову»: одна запись на вызов или пачка), inbox\_list.
2. inbox\_suggest (сохранить предложение Claude для записи: параметры и первый шаг), tasks\_processed\_count (для порога 200), tasks\_for\_learning (разобранные задачи постранично, для режима обучения), profile\_get, profile\_set (выжимка).
3. inbox\_process (разобрать запись так, как сказал пользователь в чате), items\_list (с фильтрами), task\_update, mark\_done.
4. today\_get, today\_respond (принять / отказаться / перенести).
5. routines\_today, routine\_mark, practice\_log, assignments\_list.

Начинать с первых трех строк: они нужны для разбора инбокса Claude.

## 9. Этапы

1. **Этап 0. Каркас** (2–3 дня). Worker, D1, миграции, i18n-скелет, вход через Telegram для одного пользователя, gitleaks, GitHub Actions, AGENTS.md для TaskBuddy.
2. **Этап 1. Инбокс** (≈3–4 дня). Бот: текст (в том числе диктовка с клавиатуры) → инбокс, реакция-лайк на сообщение. Вкладка «Инбокс», карточка задачи с мгновенным сохранением (без кнопки «Сохранить», черновик до последнего обязательного поля), кнопка «+». Все поля карточки (в базе, в карточке и для импорта) и таблицы всех видов записей, включая рутины, практики, зоны и инсайты, создаются сразу; вкладки и правила этих видов — на своих этапах. Вкладка «Справочники». Импорт шаблона — отдельная задача, не привязанная к этапу. Инбокс разбирает сам пользователь; помощь Claude появится на этапе 6.
3. **Этап 2а. Сегодня** (≈1,5 недели). Пять кнопок «Выдай мне дело», «Выбрать» с фильтрами по всем полям карточки, принять / отказаться, после выполнения «Дофамин» и «Обновить», «Что мешает?», список на сегодня последним сообщением, вечерний опрос 21:00, утро после пройденного опроса (условие утренних рутин — на этапе 3), напоминания; страница: вкладки «Сейчас» (пока один блок — пять задач и его кольцо, 20% за задачу), «Сегодня» (пока только блок пяти задач), «Задачи», «Инсайты». Это первая рабочая версия.
4. **Этап 2б. Таймер, награды, первый шаг** (≈1 неделя). Таймер 5/10/15/25 с паузой и четырьмя кнопками (точный будильник), «Парковка», награды и кнопка «Награда», первый шаг: голосовое в боте при «Принять», текстом на странице, иконка «глаз».
5. **Этап 3. Рутины и зоны**. Импорт твоей таблицы зон, таймер 15 минут, рутины всех периодов, вкладка «Рутины», блоки рутин и FlyLady на «Сегодня» с их кольцами на «Сейчас», галочка «сейчас» на блоках, кнопка «Утренние рутины сделаны» и условие утра для бота и карточки на странице.
6. **Этап 4. GTD целиком**. Проекты и шаги, «Разбить», «Жду», очередь, категории, «Параллельно» и кнопка «Категория», автолягушки, еженедельный обзор, прогресс, вкладки «Проекты» (кнопки «В фокус», «Отложить», «Разбить») и «Идеи» с сортировкой, блок «проекты в фокусе» на «Сегодня» с кольцом, отметка «выполнен на сегодня», не больше трех проектов в фокусе (настройка).
7. **Этап 5. Практики**. Вкладка «Практики» и блок практик на «Сегодня» с кольцом по дневному минимуму.
8. **Этап 6. Claude через MCP** (≈1 неделя). MCP-сервер на Durable Objects, вход по OAuth (токены в KV), строки 1–3 п. 8, команды «Разгрузи голову» и «Разбери инбокс», запланированная задача в Claude в 10:00, 14:00, 18:00 и 22:00 (без папки; после запуска проверить пропуски), подтверждение предложений Claude, текстовый первый шаг от Claude, режим обучения, оповещение, если Claude не заходил больше суток. Права сразу в итоговом виде: помощь Claude только владельцу подписки, по расписанию только чтение и предложения, чтобы на этапе 7 члены семьи не получили доступа к Claude.
9. **Этап 7. Семья**. Приглашения, поручения, «Я поручила».
10. **Этап 8. Публикация**. Скрипт: gitleaks по всей истории, `git archive main`, новый публичный репо одним коммитом.

Почему Claude через MCP ближе к концу: так решила владелица. Выгрузку из головы делает Claude, а не бот, поэтому все, что нужно для нее (MCP, вход, команды, запуски по расписанию, обучение), собрано в один этап перед семьей и публикацией. Инбокс, ввод текстом в бот, форма «+» и карточка остаются в ранних этапах, а до этапа 6 инбокс разбирает сам пользователь. Первая рабочая версия (этапы 0, 1 и 2а) — около 3 недель.

## 10. Риски

1. **Сам TaskBuddy станет «дофаминовой» задачей** (Claude (артефакт)). Защита: этапы короткие, каждый дает пользу сразу; после этапа 2а жить в системе неделю, прежде чем добавлять новое.
2. **Утечка между членами семьи** (нет RLS). Защита: SQL только в слое доступа, отдельные тесты прав, проверка в ревью.
3. **OAuth для MCP** — самая хрупкая часть по срокам. Защита: шаблон Cloudflare, на этапе 6 только один пользователь, семья появляется позже.
4. **Часовые пояса и летнее время** (Ирландия переходит дважды в год). Защита: UTC в базе, IANA-зона у пользователя, тесты на дни перехода.
5. **Качество диктовки** — на стороне телефона или Claude; текст всегда сначала в инбокс, его можно поправить.
6. **Перегруженная карточка задачи** (Perplexity). Защита: в карточке сначала только обязательные поля, остальное под «Еще».
7. **Лимиты Workers** — не риск: на твоем платном тарифе до 30 секунд процессора на запрос, составление плана дня укладывается с запасом.

## 11. Варианты и рекомендация

1. **A. Все на Cloudflare: Workers + D1.** Плюсы: один поставщик, привычный тебе стек, уже оплачено (Workers Paid), быстро отвечает. Минусы: привязка к Cloudflare, нет RLS. **Рекомендую.**
2. **B. Workers + PostgreSQL (Neon/Supabase) через Hyperdrive.** Плюсы: RLS, более мощный SQL, легче переехать. Минусы: два поставщика, задержка, больше настроек, бесплатная база засыпает. Запасной путь, если перерастем D1.
3. **C. Сервер на Python (VPS).** Плюсы: полная свобода. Минусы: нужно администрировать сервер, платить, нет готового MCP-шаблона с OAuth. Не рекомендую.

**Модели для разработки.** Этап 0, схема, core (выбор дня, права) и OAuth — Opus: тут ошибки дорогие и нужна точность. Страницы, тексты, рутинные обработчики — можно Sonnet, это быстрее и дешевле.
